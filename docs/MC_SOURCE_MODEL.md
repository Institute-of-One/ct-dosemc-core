# The Monte-Carlo source model, and everything it assumes

This document is the honest inventory of what the simulation does and does not
represent. It exists because the claim of IORN-007 is not "we computed organ
doses" — plenty of groups have — but "we computed them with a pipeline whose
every input, coefficient and assumption is open and inspectable". An assumption
that is not written down here is a defect.

Read alongside `docs/REPRODUCING_DATA.md` (what data, from where, under what
licence) and `results/` (every number, with its provenance record).

## 2. Building the engine

MC-GPU is vendored, unmodified, at `vendor/MCGPU` (clone of
`https://github.com/DIDSR/MCGPU`). Upstream targets Linux with `nvcc` + `gcc`;
`tools/build_mcgpu.ps1` is the Windows equivalent. It never edits the vendored
source — it patches a *copy* under `vendor/build/` and records every substitution
in `vendor/build/build_info.json` together with the SHA-256 of the original
source, the patched source and the resulting executable.

```powershell
git clone --depth 1 https://github.com/DIDSR/MCGPU.git vendor/MCGPU
# zlib 1.3.1 source into vendor/zlib-1.3.1
powershell -File tools/build_mcgpu.ps1 -Target cpu
powershell -File tools/build_mcgpu.ps1 -Target gpu -CudaSamples <clone of NVIDIA/cuda-samples>
```

### 2.1 Patches applied, and why

Four defects, of which **three produce wrong results silently**. All four were
reported upstream on 2026-08-08 -- [DIDSR/MCGPU#22](https://github.com/DIDSR/MCGPU/issues/22)
(`abs()` on a `double`), [#23](https://github.com/DIDSR/MCGPU/issues/23) (CPU PRNG
not advanced between projections), [#24](https://github.com/DIDSR/MCGPU/issues/24)
(binary files opened in text mode) and [#25](https://github.com/DIDSR/MCGPU/issues/25)
(aperture line documented in the wrong order). Full write-ups are in
[`UPSTREAM_ISSUES.md`](UPSTREAM_ISSUES.md).

0. **`abs()` on a `double` collapses any aperture below 1° to a pencil beam**
   (`MC-GPU_v1.3.cu:1386`, `:1393`). In C, `abs` is `int abs(int)`, so the
   argument is truncated before the comparison against `1.0e-7`. A 10 mm
   collimation at 600 mm SAD subtends 0.95° — an ordinary CT beam, and the
   TG-195 Case 4 beam — and silently becomes a pencil beam with no diagnostic.
   Only the CPU build is affected: `nvcc` compiles `.cu` as C++, where `abs` has
   a `double` overload. Fixed with `fabs`.

   *Caught by asserting the engine's own echoed apertures against the requested
   ones. The dose values it produced looked entirely reasonable.*

1. **`fopen(..., "w")` → `fopen(..., "wb")`** for the three files upstream marks
   `!!BINARY!!` (the projection image and the two dose `.raw` files). On Linux
   `"w"` and `"wb"` are identical; on Windows the CRT expands every `0x0A` byte
   inside the 32-bit floats to `0x0D 0x0A`. Every value read back is garbage.
   **This is a correctness fix, not a portability nicety** — without it the
   pipeline silently produces dose values wrong by tens of orders of magnitude.

2. **CPU-branch PRNG advance.** Upstream advances the seed between projections
   with `update_seed_PRNG(numprocs, total_histories, &seed_input)`, but that call
   sits *inside* `#ifdef USING_CUDA`. The CPU branch therefore replays the
   identical random sequence for every projection of a CT trajectory: the tally
   comes out exactly invariant under the rotation step, and the reported
   statistical uncertainty is meaningless. Because `init_PRNG` leaps ahead by
   `(history_batch+1) * histories_per_thread * LEAP_DISTANCE`, offsetting the
   batch index by one projection's worth of batches restores the same
   independence guarantee the CUDA branch has.

   *This was found by the four-fold symmetry check on the CTDI peripheral
   positions — the four cardinal chambers returned identical values to every
   decimal place. It is exactly the class of defect the symmetry and
   anti-fabrication tests exist to catch.*

3. **512 MB stack** (`/F 536870912`). MC-GPU declares the per-projection source
   and detector arrays and the material tables as automatic storage; MSVC's 1 MB
   default overflows before the first history (`0xC00000FD`).

4. **`cudaThreadSynchronize` → `cudaDeviceSynchronize`** (GPU target only),
   removed from the CUDA runtime in CUDA 12.

Two further MSVC-only compile flags, which change no semantics: `/TC` (the `.cu`
file is plain C in the non-CUDA path) and `/Dinline=static` (C99 `inline` with no
external definition leaves the kernel helpers unresolved under MSVC; upstream
relies on `gcc -O3` always inlining them).

### 2.2 CPU vs GPU, and what "agreement" means for gate G5

Both targets compile the same physics from the same source. The CPU target needs
no CUDA toolkit and is the reference build; the GPU target is 20–40× faster and is
what Phase 2 requires for a cohort. **Any number that appears in the paper must be
shown to agree between the two builds** — that check is not yet done.

G5 is not a formality. Defect #22 (`abs()` on a `double`) manifests *only* in the
CPU build, because `nvcc` compiles `.cu` as C++ where `abs` has a `double`
overload. A defect that makes the two builds disagree for identical input is
exactly what this gate exists to catch, and it has already produced one.

**How tight should the agreement be?** Read from the source, so the acceptance
criterion is set before the numbers exist rather than after:

* The dose tally accumulates **scaled integers**, not floats:
  `atomicAdd(&voxels_Edep[v].x, __float2ull_rn(Edep * SCALE_eV))`
  (`MC-GPU_kernel_v1.3.cu:435`, `SCALE_eV = 100.0f`). Integer addition is exactly
  associative, so *accumulation order contributes nothing* — unlike a
  floating-point atomic, where thread scheduling alone would produce run-to-run
  drift. There is no "it's just atomics" excuse available for a discrepancy.
* Both builds seed from the same rule, `init_PRNG(batch, histories_per_thread,
  seed_input)` leaping `(batch+1) * histories_per_thread * LEAP_DISTANCE`, with the
  batch index being the global thread id on the GPU (`:198`) and the loop counter
  on the CPU (`:200`). With `histories_per_thread` and the thread/batch count
  matched, the two builds simulate **the same set of histories**.

So the differences that legitimately remain are the float→integer rounding mode
(`__float2ull_rn`, round-half-to-even, against the CPU's `(ull)(x + 0.5f)`) and
fast-math divergence between `nvcc` and MSVC in the transcendentals. Both are
far below the statistical noise.

**Criterion: agreement much tighter than the Monte-Carlo statistical uncertainty.
A discrepancy merely "within statistics" is a finding to investigate, not a
pass.** Anything larger is a defect, and is to be reported rather than rounded
away.

Overflow, worth knowing before a long cohort run: the tally is
`unsigned long long` scaled by `SCALE_eV`, so it saturates above
`1.8e19 / SCALE_eV` eV in a single voxel (upstream's own warning at `:462`).

## 3. What MC-GPU models

* **Photon transport only.** Rayleigh, Compton (relativistic impulse
  approximation) and photoelectric absorption, cross-sections from PENELOPE 2006.
* **Woodcock (delta) tracking** through the voxel grid, so voxel boundaries are
  never explicitly crossed. Cheap, unbiased, but slow if a very dense voxel
  (metal implant) is present.
* **Dose tally** = energy deposited per voxel, reported as `eV/g per history`
  with a per-voxel relative uncertainty at 2σ.

## 4. What it does *not* model — the assumption list

These are the things a reviewer will ask about. Each is either handled by a
documented approximation or declared as a limitation.

### 4.0a The low-energy cutoff, and what it costs (measured: nothing)

MC-GPU has no independent absorption energy. The cutoff **is** the lower bound of
the material tables: when a photon's energy falls below the first tabulated
entry, the interpolation index goes negative and the track is discontinued
(`MC-GPU_kernel_v1.3.cu:311`, `:372`). The two absorption paths differ, and the
difference is worth knowing:

* **Photoelectric** — `randno = -energy` (`:351`): the *entire* photon energy is
  deposited locally. Nothing is lost.
* **Compton below the cutoff** — only the energy transferred to the electron is
  tallied (`:301`); the photon's **residual energy is discarded, not deposited**.

That second path is a genuine energy leak, and it should fall preferentially on
scatter-fed regions, since those are reached by the multiply-scattered photons
that have degraded furthest. It was therefore a candidate for the residual −0.8%
at the TG-195 centre VOI.

**It is not the explanation.** Regenerating the material tables down to 1 keV
(`tools/make_materials.py --e-min-ev 1000`) and re-running the 120 kVp first test
moved every scored segment by ≤0.012% — inside the Monte-Carlo noise:

| | 5 keV tables | 1 keV tables |
|---|---|---|
| segment 1 | −0.198% | −0.198% |
| segment 2 | −0.052% | −0.052% |
| segment 3 | −0.338% | −0.334% |
| segment 4 (scatter-fed) | +0.222% | +0.210% |

The reason is physical: at 5 keV in PMMA the photoelectric cross-section so
dominates that almost no photon Compton-degrades *past* the cutoff — it is
absorbed first, with its full energy deposited. The 5 keV tables are kept as the
default; `--material-emin-kev` selects others, and the measurement above is the
justification for not bothering.

### 4.1 Electrons are not transported

The dose tally is rigorously a **collision kerma** estimate: photon energy is
deposited at the interaction site. At CT energies in soft tissue the
secondary-electron range (≲0.1 mm at 120 keV) is far below any voxel we use and
charged-particle equilibrium holds, so kerma ≈ absorbed dose. It does **not** hold
at low-density interfaces (lung boundaries, bowel gas) or inside air cavities.
Consequence: air-filled regions cannot be scored directly with usable statistics,
which is why the CTDI chamber positions are scored in PMMA (§5.2).

### 4.2 No bowtie filter

MC-GPU v1.3 has no bowtie, and real bowtie geometry is vendor-proprietary. The
current simulation therefore uses a **flat fan** — the fluence is uniform across
the fan angle. This is the single largest known bias against a *real scanner*:

* the periphery of the phantom receives relatively more fluence than on a real
  scanner, so the central/peripheral dose ratio is biased **low**;
* the beam is not hardened off-axis, so the peripheral spectrum is too soft.

It is **not** a defect for the Phase-1a gate: AAPM TG-195 Case 4 specifies a
source with no bowtie, so the flat fan is the specification there (§5.0). The
bowtie is a Phase-1b item (G6), implemented as a per-sub-fan spectrum rather than
as a wedge in the voxel geometry — see §5.2. Until it exists, no number from this
pipeline should be compared to a measured scanner CTDI without that caveat.

### 4.3 Point focal spot

No focal-spot size, no extra-focal (off-focus) radiation, no focal-spot motion
(flying focal spot). Focal-spot blurring has a negligible effect on dose at
distances of tens of centimetres; off-focus radiation adds a few percent of tube
output at large angles and is neglected.

### 4.4 Spectrum

SpekPy supplies the spectrum from kVp, anode angle and added filtration. The
inherent filtration of the tube is SpekPy's model value, not the real tube's.
The added filtration is currently a **free parameter chosen to reproduce a stated
HVL**, and the HVL used for that match is reported with every run. Real CT tubes
also carry a flat filter of Ti or Cu on some vendors; where the vendor states it,
it is entered explicitly rather than absorbed into an equivalent Al thickness.

The spectrum is resampled onto at most 255 bins because MC-GPU compiles with
`MAX_ENERGY_BINS = 256`. Resampling conserves the photon count per bin, not the
differential fluence at the bin centre, and the retained photon fraction is
recorded in every results file.

### 4.4a The air that is not there

MC-GPU moves each photon from the focal spot to the voxel bounding box in a
straight line **without interaction**. Whatever lies outside the box — the air
gap between the tube and the patient, the couch, the gantry cover — simply does
not exist. This is easy to overlook because it never produces a warning.

Measured on TG-195 Case 4, where the source sits 44 cm beyond the phantom surface
in air: modelling 1 cm of that path instead of 44 cm biases the scored energy by
about **+0.8%**, and the bias falls monotonically to ≈0 as the modelled path
approaches the full distance (§5.3). It matters just as much for patient
geometry, where the same 40–50 cm of air sits between the focal spot and the skin.

Consequence for Phase 2: the voxel box must extend far enough transversely to
carry the air path, or the omission must be quantified and corrected. The
transverse and longitudinal margins are separate parameters for exactly this
reason — the beam travels in the scan plane, so only the transverse margin needs
to be large, which is the difference between a 9-million-voxel geometry and a
130-million-voxel one.

### 4.5 Absolute normalisation

MC-GPU knows nothing about mAs. The bridge is:

```
N_Omega  = Phi(z) * z^2                     photons / sr / mAs   (SpekPy)
Omega    = 2 sin(theta_ap/2) * phi_ap       sr                   (MC-GPU sampling)
N_hist   = N_Omega * Omega * mAs            photons
D [mGy]  = d [eV/g/history] * N_hist * 1.602176634e-16 * 1e3
```

`Omega` follows from MC-GPU sampling `cos(theta)` and `phi` uniformly
(`MC-GPU_kernel_v1.3.cu:652`, aperture convention at `MC-GPU_v1.3.cu:1378`).

SpekPy applies **no** air attenuation between the focal spot and its reference
distance: `Phi(z) * z^2` is exactly invariant from z = 1 cm to z = 200 cm, and the
HVL does not change with z. That is measured, not assumed — see
`tests/test_spectra.py::test_spekpy_applies_no_air_attenuation_between_the_focus_and_z`.
Had it been otherwise, every absolute dose would have been low by a few percent
over a metre of air.

This makes the absolute dose **entirely dependent on SpekPy's absolute tube
output**, which is a model of an ideal tube and not a calibration of any real
scanner. Gate G0 measures how far that model sits from another published one:
against the IPEM-78-derived spectra TG-195 distributes, a SpekPy beam of the same
nominal tube (120 kVp, 11° W anode, 2.861 mm Al) is about **7.7% softer in HVL**
and 1.4% lower in mean energy — a difference between tube models, not a defect in
either, but not something to absorb silently.

For patient dose the intended anchor is different and stronger:
normalise so that the simulated free-in-air air kerma at the isocentre reproduces
the scanner's stated output, or so that the simulated CTDIvol reproduces the
CTDIvol recorded in the DICOM/RDSR. Which normalisation was used will be stated
per result. Until the bowtie exists, neither is trustworthy.

### 4.6 Geometry

* The CT trajectory is a circle about **Z** with an optional constant
  longitudinal translation per projection (helical). Continuous rotation is
  approximated by `N` discrete projections; `N` is reported and its adequacy is a
  convergence check, not an assumption.
* No anti-scatter grid, no curved detector, no gantry, no patient table. Table
  attenuation is a real few-percent effect on posterior organ dose and is
  currently **missing**.
* No tube-current modulation in Phase 1 (a CTDI acquisition is fixed-mA by
  definition). Phase 2 reads I(z) from DICOM (0018,1151) and applies it as a
  per-rotation mAs.

### 4.7 Phantom discretisation

Voxel membership is decided by voxel centre, so curved surfaces are stair-stepped.
For the CTDI phantom, the peripheral chambers sit 1 cm below a curved surface in a
steep dose gradient, so the result is voxel-size dependent; a convergence check
over voxel size is required before any number is quoted.

## 5. Validation: code verification first, physical anchor second

### 5.0 Why the gate changed

The first attempt made the Phase-1 gate "reproduce a measured CTDIvol". That was
the wrong criterion, and it is worth stating why, because the reasoning applies to
the whole project.

The simulated system has no bowtie, a flat fan, a homogeneous PMMA cylinder and a
point source. Every published CTDIvol was measured on a real scanner with a
bowtie. The two are not comparable, so any disagreement is **unattributable** —
it could be a coding error or a missing physical component, and no amount of
argument decides between them. Judging the central/peripheral ratio of 0.293
against a literature "≈0.5" was comparing two different experiments.

**AAPM TG-195 Case 4 specifies the configuration we already have**: a PMMA
cylinder of radius 160 mm, an isotropic point source at 600 mm, a flat fan with no
bowtie, and energy scored directly in PMMA in eV per emitted photon. Four
independent Monte Carlo packages published results for it. It is the de-facto
standard for verifying a CT dose Monte Carlo, and it is free to download.

Three obstacles vanish at that gate, none of them by being ignored:

| Obstacle | Why it does not apply to TG-195 Case 4 |
|---|---|
| no bowtie model | Case 4 has no bowtie — the flat fan is the specification |
| PMMA → air-kerma conversion | Case 4 scores energy deposited in PMMA directly |
| absolute mAs normalisation | the unit is per emitted photon, so SpekPy's absolute output drops out |

Reproducing a measured CTDIvol remains a goal. It moves to **Phase 1b**, where it
belongs: a test of the *scanner* model, once the *code* is known to be right.

### 5.1.1 Which TG-195 sub-case a run is compared against

The second test is published **twice** — 36 discrete projections at 10° steps, and
a source angle sampled per photon from the continuous 360° distribution.
`read_case4_reference(..., angular=...)` selects the column and the runner picks it
from the projection count; comparing our 36-projection run against the continuous
column was worth −2.1% on its own.

**The two columns do not have the same population of contributing codes**, and
that, rather than any physical inconsistency, is why they differ. In the
distributed workbook only **Geant4 and MCNP** submitted the continuous sub-case;
the cells for EGSnrc and PENELOPE are empty. The `Mean` sheet's continuous row is
therefore a **two-code** average, while its discrete rows are four-code averages.
The arithmetic is checkable by anyone holding the file:

```
Geant4 continuous centre 11.1821
MCNP   continuous centre 11.1067
              average    11.1444   = the Mean sheet's continuous centre, exactly
```

The two submitting codes also disagree with their *own* discrete results, by
+2.23% / −0.61% (Geant4) and +2.51% / +2.58% (MCNP) at centre / perimeter. So the
continuous column carries an effective uncertainty far larger than the report's
nominal 1%, and the earlier note here — that the centre VOI showed an
"unexplained anomaly" — was comparing a two-code number with a four-code number.
It is withdrawn.

**This project uses the discrete sub-case as its reference**, and reproduces its
conditions with 36 discrete projections. The discrete column has all four codes,
with an inter-code spread of 1.01% at the centre VOI and 0.19% at the perimeter.

The four packages disagree with each other by 1.01% at the centre, so quoting a

* **The perimeter VOI agrees with every one of the four codes to within ±0.12%,

* The closest code at both VOIs is essentially **PENELOPE**, and that is not a

  suspect.

### 5.1.3 Both sub-cases, run here

Rather than only choosing between the published columns, both sub-cases were run
with this pipeline: 36 discrete projections, and 720 projections as the
continuous limit. Same geometry, same statistics, one azimuthal sub-fan in both,
so the sub-fan solid-angle bias is common to the pair and cancels in the
comparison.

| | discrete (36) | continuous limit (720) | difference |
|---|---|---|---|
| centre | 11.3251 | 11.2878 | **+0.330%** |
| perimeter | 39.7987 | 39.7560 | **+0.107%** |

For comparison, the two packages that submitted both sub-cases to TG-195 disagree
with *themselves* by +2.23% / −0.61% (Geant4) and +2.51% / +2.58% (MCNP) at
centre / perimeter.

This is worth stating in the manuscript, because it makes the point without
criticising the reference: **the two angular sub-cases of this pipeline agree with
each other to 0.33% and 0.11%, where the two reference codes that reported both
differ from themselves by up to 2.6%.** The sign is also physically right — a
36-point quadrature of an angular function that swings by a factor of 225 should
sit slightly above its own continuum limit.

G1 is run **first** on purpose. It removes the spectrum, the rebinning, the
255-bin limit and the source rotation from the problem: if the monoenergetic
single-projection case disagrees, nothing downstream of it means anything.

**Phase 2 (patient cohort) is released by G0–G5, not by G6–G9.**

The CTDI results already in `results/` belong here, and none of them is a
validated reproduction of a measured CTDIvol. The dimensionless ratios reported
alongside them (central/peripheral, four-position spread) were the right thing to
report *given* that a measured comparison was unavailable, but they are still
comparisons against bowtie-equipped scanners and are moved here with that caveat
attached.

#### The bowtie: sub-fan decomposition, not a wedge in the geometry

The earlier plan was to place an aluminium wedge in the voxel geometry. MC-GPU has
only voxel geometry, so a wedge near the focal spot would mean extending the voxel
grid all the way to the source — which is exactly the cost that makes the TG-195
air path expensive (§5.3).

The chosen approach instead splits the fan into K azimuthal **sub-fans**, each run
as its own MC-GPU invocation and combined by solid-angle weight. A bowtie then
becomes a per-sub-fan spectrum: attenuate the SpekPy spectrum through the fitted
bowtie thickness `t(ψ_k)` before writing sub-fan `k`'s spectrum file. This gives
**both** fluence shaping and off-axis beam hardening, costs no extra histories,
touches no MC-GPU source, and reduces the bowtie to a single published
angle-versus-equivalent-thickness profile that ships in `results/` as data.

That machinery is already built and in use — TG-195's field is a rectangle on the
isocentre plane, which is not the same shape as MC-GPU's `(cos θ, φ)` rectangle,
and sub-fans are what reconciles them (§5.3).

### 5.3 What the approximations are actually worth

Each "we modelled it this way instead" is a claim about a number.
`tools/run_tg195.py --scan PARAM=v1,v2,...` turns each into a measurement against
the TG-195 reference. Measured so far, on the Case 4 first test:

* **Air path — the largest effect, and previously invisible.** MC-GPU jumps each
  photon from the focal spot to the voxel bounding box *without interaction*, so
  air outside the box does not exist. TG-195 fills the geometry with air and puts
  the source 44 cm beyond the cylinder surface. Modelling 1 cm of that instead of
  44 cm biases the scored segments by about **+0.8%**; the deviation falls
  monotonically to ≈0 as the modelled path approaches the full 44 cm. This is not
  a TG-195 quirk — it applies to every patient simulation, where the air gap and
  the table sit outside any sensible voxel box.
* **Fan discretisation.** A single aperture overshoots the specified solid angle
  by 1.14%; K = 8 sub-fans reduce that to 0.014%. Measured and predicted change
  agree to 0.001% (K = 4 → 16 moved the answer by 0.066% for a predicted 0.066%),
  which confirms the effect is pure normalisation.
* **Voxel size.** 2.5 mm → 1.25 mm moved segment 1 by 0.02%. In a homogeneous
  cylinder, voxel size affects only the boundary of the cylinder and of the VOIs,
  not the transport, because Woodcock tracking does not resolve voxel walls.
* **Sub-fan count.** Worst deviation from the TG-195 mean is 0.058% at K = 4,
  0.417% at K = 8 and 0.080% at K = 16 — all inside the gate, and the spread
  between them is consistent with the Monte-Carlo noise of those runs rather than
  with any residual geometric bias.
* **Phantom length.** 40 → 200 cm moves the answer by at most 0.4%, with no trend,
  so the specified 3,000 mm "infinite cylinder" is not needed at these VOIs. Runs
  use 40–60 cm and record the fact. Re-measured on the *centre* VOI at 120 kVp
  (§5.3.2), which is where a long-range-scatter deficit would show, with the same
  answer.

### 5.3.2 The residual −0.8% at the centre VOI: both candidates eliminated

The perimeter VOI agrees with all four codes to ±0.12% while the centre sits 0.8%
below their mean, and the asymmetry is informative: the perimeter is dominated by
primary photons entering on the near side, the centre by scatter that has crossed
roughly 16 cm of PMMA. A deficit confined to the centre therefore points at
scatter transport rather than at geometry, normalisation or the beam — all of
which the perimeter would have exposed. Two mechanisms could produce it, and both
were tested rather than argued:

1. **Phantom length** — the centre VOI collects the longest-range scatter, and the
   specification is 3,000 mm. Re-run on the centre VOI at 120 kVp (the earlier
   scan was the monoenergetic first test, where the scatter travels differently):
   worst deviation **0.806% / 0.781% / 0.858%** at 40 / 100 / 200 cm. Flat, no
   trend. *Not the explanation.* The 300 cm point did not complete and is not
   claimed.
2. **Low-energy cutoff** — see §4.0a: ≤0.012% at 1 keV versus 5 keV tables.
   *Not the explanation.*

The residual is therefore recorded as a residual. In context: the four reference
codes disagree with each other by 1.01% at this VOI, and our value sits 0.22% from
the nearest of them — which is PENELOPE, the package that shares our
cross-section library. A −0.80% deviation from a four-code mean whose own spread
is 1.01% is not a validation failure, and it is reported alongside the per-code
comparison (§5.1.2) rather than alone.

### 5.3.1 The volume of a scored region is not a detail

Two regions in this project are defined analytically and then voxelised, and both
were wrong by amounts that mattered:

| Region | Voxel-centre volume / true volume |
|---|---|
| TG-195 second-test VOI (10 mm ø, 2.5 mm voxels) | **0.955** (−4.5%) |
| CTDI pencil chamber (13.1 mm ø, 2.5 mm voxels) | **1.113** (+11.3%) |
| TG-195 first-test section (320 mm ø) | 1.002 (+0.2%) |

Energy deposited is proportional to the selected volume, so the first of these
came straight off the G2 result. `phantom.cylinder_occupancy` replaces the
centre-inside test with the analytic volume fraction per voxel (exact in z,
subdivided only on the boundary ring), reproducing the true volume to 7.5×10⁻⁵.

**It is applied only where the region floats inside a uniform medium.** The
first-test VOI's edge *is* the phantom edge, which the geometry itself voxelised
with a centre test, so a voxel whose centre is inside is entirely PMMA and its
whole mass genuinely absorbed dose; weighting it down discards real deposited
energy at the entrance surface, measured at −2.2%. And it is never applied to a
segmentation mask, because such a mask *is* the definition of the organ — there is
no analytic shape for a voxel to be partially inside of.

## 6. The CTDI anchor (Phase 1b)

### 6.1 Geometry

IEC 60601-2-44 dosimetry phantom: homogeneous PMMA (ρ = 1.19 g/cm³, PENELOPE
material #224) cylinder, 15 cm long, 32 cm diameter (body) or 16 cm (head),
surrounded by dry air (#104). The bores are **not** cut out: a real measurement
plugs the four unused bores with PMMA rods, so a homogeneous cylinder is the
closer model.

Chamber regions are cylinders of 1.31 cm diameter and 10 cm length — the volume a
100 mm pencil chamber occupies — on the axis and at 1 cm depth at the four
cardinal positions.

### 6.2 What is reported, and the gap that remains

`CTDI100 = (1/(N·T)) ∫ D(z) dz` over ±50 mm. The Monte Carlo's mean dose over the
chamber volume *is* that integral divided by the chamber length, so
`CTDI100 = D_mean · L / (N·T)`.

**The reported quantity is absorbed dose to PMMA, not air kerma in a bore.** The
conventional CTDI is air kerma; converting needs
`(μ_en/ρ)_air / (μ_en/ρ)_PMMA` averaged over the local, hardened spectrum. That
conversion is **not implemented yet**. Scoring the air cavity directly is not a
workaround — MC-GPU's analogue tally gives hopeless statistics in 3 mg of air
(§4.1). The planned route is to compute μ_en/ρ for both media from open,
public-domain elemental data (NIST XCOM / Hubbell & Seltzer) via the mixture rule,
carry it as provenance, and report the sensitivity of the factor across the
spectrum range.

Until then the meaningful comparisons are **dimensionless**, and insensitive to
that factor to first order:

* central / peripheral CTDI100 ratio;
* the spread across the four peripheral positions, which must be consistent with
  the quoted Monte-Carlo uncertainty (a *sensitive* test — see §2.1);
* HVL against published CT values;
* free-in-air air kerma at the isocentre, computed by SpekPy without the Monte
  Carlo at all.

**But note what these can and cannot settle.** Every published central/peripheral
ratio was measured on a scanner with a bowtie, and this simulation has none, so
the comparison is between two different experiments. The measured ratio of 0.293
against a literature "≈0.5" is *expected* — a flat fan over-illuminates the
periphery — and is not evidence of an error. It becomes a real test only after G6
(bowtie) and G7 (filtration matched to a measured HVL). Code correctness is
settled by TG-195 (§5.1), not here.

### 6.3 Uncertainty

MC-GPU reports a per-voxel relative error at 2σ; `mcgpu_io.read_dose_map`
converts to 1σ immediately. Region uncertainties combine per-voxel σ in
quadrature, which treats voxel tallies as independent. **They are not** — a single
photon can deposit in many voxels — so this *understates* the region uncertainty.
The observed spread across the four (physically equivalent) peripheral chambers is
therefore reported as an independent, and more trustworthy, estimate. Where the
two disagree, the larger is quoted.

The measured understatement on the Phase-1 CTDI run was a factor of **7.2**. That
figure is itself a weak estimate: a sample standard deviation from four points has
three degrees of freedom, so its own relative uncertainty is about
`sqrt(1/(2·3)) ≈ 41%`. Honestly stated, the quadrature estimate understates σ by
**roughly 4× to 13×**, and writing "7.2×" without that interval claims more
precision than four points can carry.

An independent-replica estimate (K ≥ 10 runs, different seeds, sample standard
deviation of the reported quantity) brings that down to ≤23% and is the intended
final method — gate G4.

**G4 has now been run on TG-195 Case 4, K = 10.** Even the sub-fan quadrature —
which combines *genuinely* independent engine invocations and so is not obviously
biased — understates the replica SD:

| VOI | replica SD | relative | sub-fan quadrature | ratio |
|---|---|---|---|---|
| segment 1 | 3.76 | 0.033% | 1.99 | 1.9× |
| segment 2 | 1.91 | 0.074% | 0.96 | 2.0× |
| segment 3 | 1.90 | 0.108% | 0.80 | 2.4× |
| segment 4 | 2.76 | 0.208% | 0.69 | 4.0× |

With K = 10 the SD is itself known only to 1/√(2(K−1)) = 24%, so these ratios are
roughly 1.5–5× rather than the printed figures. The conclusion is unchanged and
applies to every uncertainty this project reports: **quote the replica SD, and
where only an in-run estimator is available, say that it is a lower bound.**
