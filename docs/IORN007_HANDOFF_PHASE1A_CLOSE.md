## タスク A — G2 を閉じる

### A1. 部分体積マスクを実装する

`ct_dosemc_core/dosimetry.py`：

```python
def region_dose(name, dose_map, mask, density_g_cm3, n_histories, *, weights=None):
    """weights: mask と同形の float 配列。各ボクセルの VOI 内体積占有率 f_i in [0,1]。
    None なら従来どおりブール（全 f_i = 1）。"""
```

`m_i = f_i · ρ_i · v³` として質量・平均線量・σ をすべて重み付きで計算すること。
既定 `None` で従来動作を厳密に保つ（既存テストが壊れないこと）。

`ct_dosemc_core/tg195.py`：

* `second_test_voi_masks()` を、ブールマスクと同時に占有率配列を返すように拡張
  （`(mask, weights)` のタプル、または新関数 `second_test_voi_weights()`）。
* 占有率は各ボクセルを **32³ 以上**に細分して解析円柱内の割合を数える。
  境界ボクセルだけ細分すれば十分速い。
* 単体テスト：占有率の総和 × ボクセル体積が解析体積 π·(0.5)²·10 = 7.85398 cm³ に
  **相対 1e-3 以内**で一致すること。

## タスク B3 補足 — GPU ビルド（GO。RTX 3080 / compute capability 8.6）

Shuji さんの承認済み。CUDA Toolkit を導入して GPU ターゲットをビルドすること。
MC-GPU v1.3 は 2012 年のコードなので、現行ツールチェーンとの摩擦が予想される。
**以下の4点を先に確認してから着手すれば、往復が減る。**

### 1. MSVC のバージョン（最大の関門）

`vendor/build/build_info.json` は `Microsoft Visual Studio\18\BuildTools` を記録している。
nvcc はサポート対象の MSVC バージョンをハードコードで持っており、
新しすぎるとホストコンパイラの検出段階で
`unsupported Microsoft Visual Studio version` を出して止まる。

対処は順に：

1. `nvcc -allow-unsupported-compiler ...` を試す（多くの場合これで通る）
2. 通らなければ **VS 2022 の v143 ツールセットを併存インストール**し、
   `-ccbin "<path to VS2022 cl.exe>"` で明示指定する
3. どちらの経路を採ったかを `vendor/build/build_info.json` に記録すること
   （CPU 側と同じく、どのコンパイラで作った実行ファイルかが provenance の一部）

### 2. `-arch` フラグ

RTX 3080 は **sm_86**。upstream の `Makefile` は `sm_20` 世代の指定を持っており、
現行 nvcc はこれを拒否する。`-arch=sm_86`（または `-gencode arch=compute_86,code=sm_86`）に
置き換えること。`build_mcgpu.ps1` の引数にして、記録に残す。

### 3. `cuda-samples` の Common ヘッダ

`helper_cuda.h` / `helper_string.h` は **CUDA 11.6 以降、Toolkit に同梱されない**。
`https://github.com/NVIDIA/cuda-samples` を別途 clone し、
**導入した Toolkit のバージョンに対応する tag** をチェックアウトすること
（tag がずれるとヘッダが合わない）。clone 先とコミットハッシュを記録する。

### 4. CUDA のバージョン選択

CUDA 12.x を第一候補とする。既に `cudaThreadSynchronize` → `cudaDeviceSynchronize` の
パッチ（#4）を用意済みなので、主要な非互換は潰してある。
**それでも通らない場合は CUDA 11.8 に落とすこと** — 11.8 は sm_86 を完全にサポートし、
旧世代コードに対して寛容で、Ampere 世代の実質的な最終安定版である。
どちらを使ったかは結果 JSON の `environment` に必ず入れる。

### G5 が本当に効くゲートである理由（重要）

**欠陥 #1（`abs()` を `double` に適用）は GPU では発火しない。**
nvcc は `.cu` を C++ として翻訳するので `abs(double)` のオーバーロードが解決される。
つまり **同一入力・同一シードで CPU と GPU の結果が食い違う**。
これは仮定ではなく、このコードで実際に起きる。

したがって G5 は形式的な確認ではなく、**この種の欠陥を捕まえるために存在するゲート**である。
不一致が出た場合、それは「GPU の丸め誤差」ではなく **新しい欠陥の可能性が高い**。
安易に許容誤差を広げて通さないこと。止めて報告すること。

### 併せて確認すること

* **GPU 側の再現性。** MC-GPU v1.3 が線量タリーを整数の `atomicAdd` で積んでいるなら、
  スレッドの実行順に依らずビット単位で再現する。浮動小数の `atomicAdd` なら再現しない。
  **どちらかをソースで確認し、`docs/MC_SOURCE_MODEL.md` に明記すること。**
  固定シード再現性テスト（`tests/`）の合格基準がこれで変わる。
* **速度実測。** G2 を GPU で 1 本走らせ、CPU 比の実測倍率を記録する。
  Phase 2 のコホート計算時間の見積りに直結する。
