# TG-195 Case 4 の「2.13%」の正体 ―― 参照列は 2 コードと 4 コードの平均で、母集団が違う

**日付:** 2026-08-08
**対象:** `dc1f547` 時点の Phase-1a、および `data/tg195/09-Case 4 Results.xlsx`
**査読者:** Claude (claude-opus-5) / Cowork
**方法:** 配布スプレッドシートの `Mean` / `EGSnrc` / `Geant4` / `MCNP` / `Penelope` 各シートを直接読み、
コード別に再集計した（120 kVp, t = 10 mm, Second Test）

---

## 1. 結論

`Mean` シートの **Continuous 行は 4 コードの平均ではなく、2 コードの平均**です。
**EGSnrc と Penelope は Second Test の Continuous を提出していません**（該当セルが空欄）。
Discrete のほうは 4 コードすべてが提出しています。

算術で確認できます：

```
Geant4 continuous center 11.1821
MCNP   continuous center 11.1067
                平均      11.1444   ← Mean シートの continuous center と完全一致

Geant4 continuous perim  39.9928
MCNP   continuous perim  38.7289
                平均      39.36085  ← Mean シートの continuous perim (39.36083) と一致
```

つまり **discrete と continuous は同じ母集団の 2 通りの計算ではなく、参加コードが違う 2 つの数字**です。
「対称性から差はゼロのはずなのに 2.13% ある」という疑問は、
**そもそも同じものを比べていなかった**、という形で解けます。

さらに、提出した 2 コードは自分自身の discrete 結果とも一致していません：

| | center disc/cont | perimeter disc/cont |
|---|---|---|
| Geant4 | **+2.23%** | −0.61% |
| MCNP | **+2.51%** | +2.58% |

MCNP は 8 セル全部で discrete が continuous より +1.7〜+3.8% 高く、系統的。
Geant4 は −1.47% 〜 +2.23% で符号が定まりません。

**したがって Continuous 列は、公称 1% よりはるかに大きい実効不確かさを持ちます。**

`§5.1.1` の記述を「参照側の説明できない異常」から、次の趣旨に書き換えてください：

> TG-195 Case 4 の Second Test には Discrete と Continuous の 2 つの下位ケースがあるが、
> 配布データにおいて Continuous を提出しているのは 4 コード中 2 コード（Geant4, MCNP）のみで、

## 3. コード別に見ると、G2 の評価が変わる

「4 コード平均に対して −0.80%」ではなく、**コード別**に見てください。

**120 kVp, t = 10 mm, Second Test, Discrete**

| コード | center | ct_dosemc_core (11.291) との差 | perimeter | 同 (39.775) との差 |
|---|---|---|---|---|
| EGSnrc | 11.3956 | −0.92% | 39.7663 | **+0.02%** |
| Geant4 | 11.4314 | −1.23% | 39.7477 | **+0.07%** |
| MCNP | 11.3853 | −0.83% | 39.7286 | **+0.12%** |
| **Penelope** | **11.3162** | **−0.22%** | **39.8029** | **−0.07%** |
| 4 コード平均 | 11.3821 | −0.80% | 39.7614 | +0.03% |
| 4 コード間ばらつき | **1.01%** | | **0.19%** | |

読み取れること：

1. **perimeter は 4 コードすべてに対して ±0.12% 以内。** コード間ばらつき 0.19% より小さい。
   これは「合格」ではなく **卓越**です。そう書いてよい水準です。
2. **center は 4 コードの外側に出ているが、最も近い Penelope からわずか 0.22%。**
   コード間ばらつきが 1.01% あるので、実質的には包絡線の縁です。
3. **最も一致するのが Penelope であることには物理的な必然性があります。**
   MC-GPU の断面積は PENELOPE 2006 の PENDBASE 光子サブセットです。
   同じ断面積を使うコードと最もよく合うのは当然で、逆に言えば
   **合わなければ実装を疑うべき**ところが、合っている。
   これは論文に書く価値のある観察です。

**論文での書き方の推奨：**

> 参照コードは互いに center で 1.01% ばらつく。本手法は perimeter で全 4 コードに対し
> ±0.12% 以内、center では最近接コード（PENELOPE、本エンジンと同一の断面積系を用いる）
> に対し −0.22%、4 コード平均に対し −0.80% であった。

両方書く。片方だけ書くと後で刺されます。

## 4. 残る center の −0.8% ―― 追うべき2点だけ

perimeter が ±0.12% で合っているのに center だけ低い、という非対称には意味があります。

* **perimeter VOI は一次線が支配的**（線源に近い側の通過で決まる）
* **center VOI は約 16 cm の PMMA を通った散乱線が支配的**

つまり **輸送・幾何・正規化は正しく、散乱の到達がわずかに足りない**という形の残差です。
符号も一貫しています。候補は2つだけ：

### 4.1 ファントム長（本命）

長さスキャンで「40〜200 cm、≤0.4%、トレンドなし」と報告されていますが、確認してください：

* そのスキャンは **center VOI** について取られたか（perimeter だけなら意味が違う）
* **120 kVp** で取られたか（56.4 keV 単色では散乱の到達距離が違う）

center VOI は z 方向の長距離散乱を最も拾う場所です。仕様は 3,000 mm。
**center VOI・120 kVp に限定して 40 / 100 / 200 / 300 cm を走らせ直してください。**
0.4% 出るなら、残差 0.8% の半分がこれで説明できます。

### 4.2 MC-GPU の吸収カットオフ

MC-GPU v1.3 が光子を打ち切って局所吸収するエネルギー（`MC-GPU_v1.3.h` の
`EABS` 相当の定数）を確認し、`docs/MC_SOURCE_MODEL.md` に記録してください。
また材料ファイルのエネルギーグリッドは 5–120 keV で作られています。
グリッド下限より下の光子がどう扱われるかを**ソースで確認**すること。

カットオフが高いと、低エネルギーまで減速した散乱線が
**軸に届く前に発生地点で吸収される** → center だけが低く出る。
符号が一致します。120 kVp では絶対量は小さいはずですが、0.8% の議論では効き得ます。

**この2点で説明がつかなければ、−0.80% を残差として明記して先に進んでよい**と思います。
コード間ばらつきが 1.01% ある量で、最近接コードとの差が 0.22% なら、
それは検証の失敗ではありません。

## 5. 追加で走らせる価値が高いもの（安い、効果大）

**自分たちで Continuous 下位ケースも走らせてください。**

Geant4 と MCNP は、自分の discrete と continuous が最大 2.5% 食い違っています。
もし ct_dosemc_core の discrete と continuous が **0.5% 以内で一致**すれば、

> 参照データで両下位ケースを提出した 2 コードは互いの結果が最大 2.5% 食い違うが、
> 本パイプラインの 2 つの下位ケースは X% で一致した。

と書けます。これは**参照を批判せずに自分の内部整合性を示す**、非常に強い一文です。
計算コストは discrete 1 本と同じ。**やらない理由がありません。**

## 6. G5 の解禁（CUDA 導入 GO）

RTX 3080（sm_86）、ドライバは CUDA 13.2 対応、管理者インストール可、と確認済み。

* Toolkit は **CUDA 12.6 または 12.4** を推奨。13.x は新しすぎて 2012 年のコードには不利。
  ドライバが 13.2 対応なら 12.x は問題なく動く。
* `nvidia-cuda-nvcc-cu12` のような pip 経由は Windows では `ptxas.exe` しか入らず不可、
  という判断は正しい。**公式インストーラを管理者権限で入れる**のが唯一の道。
* MSVC のバージョン問題（Visual Studio 18 BuildTools）は
  `-allow-unsupported-compiler` → 駄目なら VS 2022 v143 併存、の順で。
* `cuda-samples` は Toolkit と**同じ tag** を clone。
* `-arch=sm_86` に置き換え。

**G5 が形式的でない理由（再掲）：** 欠陥 #22（`abs()` を `double` に）は
nvcc が C++ として翻訳するため **GPU では発火しません**。
CPU と GPU で答えが違う。不一致を丸め誤差として許容しないこと。

**併せて：** MC-GPU が線量を整数 `atomicAdd` で積んでいるか浮動小数で積んでいるかを
ソースで確認し、GPU 側の固定シード再現性がビット単位か統計的かを
`docs/MC_SOURCE_MODEL.md` に明記すること。テストの合格基準がこれで変わります。
